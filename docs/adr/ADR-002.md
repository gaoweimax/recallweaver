# ADR-002：双时间戳事实演变机制

## 状态

已采纳（v1.0.0）

## 背景

大模型从对话中提取的事实可能随现实变化，例如用户搬家、偏好改变或原有信息被更正。若直接覆盖旧事实，系统会丢失历史上下文；若只保存写入时间，也无法说明旧事实何时失效或新事实从何时开始成立。Agent 因而可能把不同时间点的事实混为当前状态，产生时序错误。

RecallWeaver 需要在保留历史信息的同时，明确区分“事实在业务世界何时有效”与“系统何时记录这条记忆”。

## 决策

不覆盖已有事实，而是使用有效时间区间保存事实演变：

- `valid_from` 表示事实业务有效期的起点。
- `valid_to` 表示事实业务有效期的终点；`NULL` 表示当前没有已知终点。
- `tx_time` 表示记忆写入数据库的事务时间点。
- 新事实与已有事实在同一租户、主体和谓词下冲突时，在同一事务内关闭旧边的 `valid_to` 并插入新边。旧记录保留以供历史查询。

`edges.valid_from` / `valid_to` 使用 UTC ISO 8601 `TEXT`；`memories.valid_from` / `valid_to` 与 `tx_time` 使用 Unix 秒 `INTEGER`。两张表的类型和粒度不同，调用方必须依据字段所属表解释时间值。当前公开写入 API 默认把有效起点设为写入时刻；延迟获知场景需要更高层提供单独的业务时间能力。

此设计是有效时间加写入时间的轻量模型，并非完整双时态数据库：当前 schema 没有事务时间终点，也不会自动保存每次更新前的数据库快照。

## 后果

**收益**

- 当前事实可用 `valid_to IS NULL` 找到，旧事实仍可审计并按时间线查询。
- 冲突关闭旧区间和创建新版本在同一 SQLite 事务中完成，失败时整体回滚，不会只留下半次更新。
- 业务有效时间与系统写入时间分离，为区分“何时发生”和“何时获知”提供了基础。
- 保留旧事实有助于检索回答历史问题，而不需要推断被覆盖的数据。

**代价与边界**

- 每次事实变化都增加历史行，读取当前状态必须显式筛选有效区间。
- 区间排序与比较需统一时区和格式；`edges` 的 ISO 时间与 `memories` 的 Unix 时间不可直接混用。
- 由于缺少事务时间区间和变更快照，无法重建数据库在任意过去时刻所呈现的全部状态。
- 抽取器的错误事实仍可能进入历史；置信度、人工确认、纠错和来源追踪属于上层策略。
