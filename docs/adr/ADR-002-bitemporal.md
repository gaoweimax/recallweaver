# ADR-002：保留业务有效时间与数据库写入时间

## Context

Agent 记忆会随现实变化。例如地址或偏好更新后，旧事实可能曾经正确，但不再当前有效。若直接覆盖旧正文，系统将失去旧值及其有效区间，也无法区分事实何时发生变化与系统何时记录变化。RecallWeaver 的记忆表因此需要表达有效时间，并保留记录的写入时刻。

## Options

1. **直接覆盖旧记忆**：更新正文并只保留最新状态，数据结构简单，但历史事实不可恢复。
2. **软删除旧记录**：保留旧行并标记状态，但仅靠状态无法准确表示业务事实何时失效，也无法准确表达事实何时开始生效。
3. **保存业务有效时间和写入时间**：为记忆记录有效起点、有效终点及写入时间；冲突时关闭旧记录的有效区间并新增新记录。
4. **完整双时态版本系统**：对业务时间和数据库事务时间均保存起止区间及每次修改快照，历史重建能力更完整，但实现与存储复杂度显著提高。

## Decision

采用第三种方案。`valid_from` 和 `valid_to` 表示事实在业务域内的有效区间，`tx_time` 记录记忆行首次写入数据库的时间点。冲突处理不覆盖旧内容，而是为旧记录设置 `valid_to`、将其标记为 `expired`，再插入包含新事实的记忆行。这样能够保留已知的事实演变，并区分业务时间和系统写入时间。

当前实现是轻量的有效时间加写入时间模型，不是完整的双时态版本引擎：没有事务时间终点，也没有自动保存每次更新的旧值快照。当前 API 的默认写入将有效起点和写入时间设为同一时刻；延迟获知场景需要由上层提供不同的业务时间。

## Consequences

- 冲突更新后旧事实仍可查询和审计，不因新值写入而丢失正文。
- 查询当前事实可利用 `valid_to IS NULL` 部分索引；历史查询可按业务有效区间筛选。
- 业务有效时间与记录写入时间分别表达，支持描述“事实早已生效但系统之后才获知”的场景（前提是调用路径能写入对应时间）。
- 相比覆盖更新，需要保存多条记忆记录并维护状态和区间。
- `tx_time` 单点时间不足以重建任意过去时刻的完整数据库状态；若合规审计要求完整事务历史，需新增事务版本策略和不可变变更日志。
