# ADR-003：动态遗忘与高频噪音过滤机制

## 状态

已采纳（v1.0.0）

## 背景

长期记忆需要体现时间衰减与重复使用，但仅按检索次数强化会形成反馈循环：偶然写入的闲聊如果频繁命中，分数可能持续增长并挤占稳定的核心事实。只排序而不设置最低分数还会把低信噪比内容传递给上层 Agent，污染上下文窗口。

项目需要在有限候选集内完成即时计算、限制频率奖励的最大影响，并在结果进入 API 之前实施明确的最低分数要求。

## 决策

对候选记忆按需计算实时分数，不依赖周期性全表刷新：

```text
usefulness_boost = min(max(alpha * retrieval_count * usefulness_weight, 0), 0.5)
retrieval_factor = min((1 + usefulness_boost)**beta, 1.5)
score = base_weight * exp(-decay_lambda * delta_t) * retrieval_factor
```

当前默认 `alpha=0.1`、`beta=1.0`、`usefulness_weight=1.0`。没有独立持久化 usefulness 字段时，检索路径以现有 `base_weight` 作为逐条记忆的有用性权重。检索奖励最多将倍率提升到 `1.5`；超大 `retrieval_count` 不会造成无限增长。评分低于 `0.05` 时按冷库规则映射为零。

Retriever 先按基础权重、写入时间与 ID 排序，再限制数据库候选窗口，以免大量低权重噪音挤掉高权重事实；候选评分排序后，将低于 `0.3` 的记录截断，再应用请求 `limit`。该 `0.3` 信噪比门槛高于冷库分数归零阈值，两者负责不同阶段。

## 后果

**收益**

- 重复命中只能提供有限奖励，无法无限放大排序分数。
- 基础权重低的噪音因有用性权重较低，恶意或意外高频访问也难以越过候选优先级和最终分数门槛。
- 分数阈值在 Retriever 层执行，低分文本不会进入公开 API 的文本结果。
- 按需评分只处理有限候选，避免新增后台调度、全表更新和写入放大。

**代价与边界**

- 权重值需要由写入方正确设置；若噪音与核心事实拥有相同的基础权重，硬阈值无法单独理解语义。
- 硬阈值可能排除低基础分但确实相关的记忆，需结合真实召回评估调节。
- 检索频次本身不是可靠的用户反馈；当前方案通过封顶限制其影响，而不是把它解释为确定的有用性标签。
- FTS5/LIKE 候选召回范围、候选上限及数据库查询性能仍会影响最终结果；得分重排无法恢复未被候选查询选中的记录。
