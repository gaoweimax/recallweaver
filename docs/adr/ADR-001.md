# ADR-001：为什么拒绝 Docker 和重型图数据库？

## 状态

已采纳（v1.0.0）

## 背景

RecallWeaver 是嵌入 Python Agent、桌面工具或单机服务的长期记忆组件。其首要交付目标是易安装、可离线运行、数据可携带，以及让开发者不必先维护一套数据库基础设施。当前数据规模和工作负载以本地记忆写入、全文查询及有界关系遍历为主，不要求分布式写入或跨节点图分析。

将数据库服务器、容器运行时或图数据库作为强制依赖，会增加部署步骤、升级矩阵、凭据管理、监控、备份恢复和故障排查成本。该成本必须由明确的产品需求或实测瓶颈证明，而不是预先承担。

## 决策

采用单文件 SQLite 作为默认持久化层，以 SQLite FTS5 提供全文索引，以关系表、索引和有界递归查询实现当前图关系访问。Python 3.11.9 应用进程通过明确的数据库边界访问 SQLite；使用 SQLite 在线备份 API 制作一致性副本。

v1.0.0 不要求 Docker，也不引入 Neo4j 或同类重型图数据库。这里的“拒绝”是针对默认部署基线，而不是断言 Docker 或图数据库永远不适用：容器化可以由部署方自行选择，服务型数据库可在后续由证据驱动地引入。

## 后果

**正向后果**

- 一个数据库文件即可保存租户、文本记忆、实体、关系和时间信息；本地运行不依赖网络服务或容器守护进程。
- SQLite 内建事务、外键和 FTS5，能够支持当前的写入一致性、全文检索和局部关系遍历。
- 文件级复制与 SQLite 在线备份 API 简化开发、测试、迁移和恢复；运维脚本可独立执行健康检查与备份。
- CI 和用户安装不需要同时维护数据库镜像、驱动协议和服务凭据。

**约束与风险**

- SQLite 的写入并发和横向扩展能力不同于服务型数据库；高并发写入需要串行化、队列化或迁移评估。
- LIKE 降级、递归图查询和本地数据分析必须受候选上限和性能基准约束；SQLite 文件增长也需要监控与备份保留策略。
- 不使用 Docker 不等于无需部署管理；运行时版本固定为 Python 3.11.9，数据库文件仍需保护、备份并验证恢复。

**重新评估条件**

当并发写入延迟、数据库体量、关系查询时延、远程多客户端或跨节点可用性超出明确服务目标时，以生产负载基准、恢复目标和运维能力重新比较 SQLite、服务型关系数据库与图数据库。只有当独立服务带来的收益覆盖新增的部署与维护成本时，才修改本决策。
