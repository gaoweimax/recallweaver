# ADR-001：采用 SQLite 与纯 Python 部署

## Context

RecallWeaver 面向需要嵌入 Agent 或桌面应用的本地记忆场景。核心数据包括文本记忆、实体关系和时间有效区间，部署目标强调安装简便、离线可用、低资源占用及可移植性。初始产品不要求多机并发写入、集群级高可用或超大规模图分析。部署基础设施不应强迫使用方维护独立服务。

## Options

1. **SQLite + Python 标准库及轻量依赖**：数据库作为单个本地文件；FTS5 提供全文索引；图遍历可通过 SQL 查询实现。
2. **SQLite 外加 Docker 部署**：通过容器封装运行环境，但仍需维护容器运行时、镜像和部署配置。
3. **Neo4j 等独立图数据库**：使用成熟的图查询能力，但增加数据库服务、驱动、部署、监控、备份及版本兼容负担。
4. **传统服务型关系数据库**：支持远程多客户端和更高并发，但对单机嵌入式场景会引入额外服务运维。

## Decision

选择 SQLite 作为默认持久化层，使用 SQLite FTS5 进行全文检索，并以 Python 模块承载业务调度、图关系遍历和评分逻辑。首期不要求 Docker，也不引入 Neo4j。

Docker 本身并非不适用；当前它并不解决本项目的核心问题，却会成为本地运行的额外前置条件。Neo4j 的图能力具有价值，但当前关系规模和查询需求可由 SQLite 表、索引和递归查询支持，无需为其单独部署和维护数据库集群。数据结构与数据库接口保持模块边界，未来出现明确的并发、规模或图查询瓶颈时，可依据实测重新评估。

## Consequences

**收益**

- 安装后可在单进程内启动，不需要额外服务、容器编排或数据库凭据。
- 数据文件易于复制、备份、迁移和用于本地测试；SQLite 在线备份接口可生成一致性副本。
- FTS5、事务、外键和索引覆盖首期记忆、图谱及全文查询需求。
- 更少的运行组件降低开发环境、CI 与用户部署的维护成本。

**代价与边界**

- SQLite 的并发写入能力和横向扩展能力不等同于服务型数据库；大量并发写入需要队列化或迁移。
- LIKE 降级、复杂图遍历及大规模数据分析可能不适合无限增长的数据集，需要测量并优化。
- 进程内 Python 图算法和 SQL 查询需由项目自行测试、观测与维护。
- 不使用 Docker 并不意味着无需版本管理或备份；应用仍须采用兼容的 Python 版本并保护数据库文件。

当并发写入延迟、数据库体量、图遍历时延或多节点需求超出既定服务目标时，应以基准测试和运维需求为依据重新审议本决策。
