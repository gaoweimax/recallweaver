# ADR-003：采用按需计算的惰性衰减

## Context

记忆权重会随时间衰减，而检索排序需要使用当前分数。若周期性扫描所有记忆并持久化新分数，工作量与记忆总量成正比；即使某条记忆从未再次被访问，也会反复产生读、计算和写操作。RecallWeaver 的主要读取路径已经产生规模受限的检索候选集，适合在候选进入排序时计算实时分数。

## Options

1. **定时全表扫描并更新**：后台定期计算所有行的分数并写回；分数持久化较新，但带来持续 I/O、事务和调度成本。
2. **每次读取都预先更新整表**：不需要后台定时器，但把全表成本放到用户请求的关键路径上，延迟不可预测。
3. **按需计算候选记忆分数**：读取时根据当前时间和记录字段计算实时分数，只对实际参与检索的候选进行计算。

## Decision

选择按需计算。检索流程先使用 FTS5 或 LIKE 取候选记录，再由 `DecayEngine.calculate_score()` 根据基础权重、时间差、衰减系数和检索次数计算实时分数，最后排序并截取结果。分数低于 `0.05` 时映射为零。该路径不要求定时后台任务或每轮全表写回。

## Consequences

- 常规衰减计算成本与候选数量相关，而不是与数据库全部记忆数量相关；避免对未访问记录做周期性更新。
- 无需额外调度器或后台服务，减少部署和运行生命周期管理。
- `decayed_weight` 等持久化字段不必然代表当前时刻分数；应以检索时计算的实时分数为准。
- 候选集之外的记忆不在本次排序中计算分数；LIKE 兜底仍可能扫描文本，惰性评分不能消除查询候选阶段的成本。
- 若未来要求全库分数报表、精确冷库归档或数据库字段始终实时，可在按需评分之外设计明确的批处理/归档机制，而不是默认增加高频全表更新。
